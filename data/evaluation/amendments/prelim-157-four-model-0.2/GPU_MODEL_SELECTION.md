# A100 local-model recommendation — 2026-10-23 EDT

Recommend exactly two local checkpoints: **Qwen/Qwen3.5-9B** as local A and
**google/gemma-4-12B-it** as local B, subject to study-lead approval. Both perform
actual BF16 CUDA generation on the A100 SXM4 40GB and fit the unchanged output
allowance with native chunked prefill. This is a deployment recommendation from
limited synthetic diagnostics, not a finding from the trustworthiness experiment
or an exhaustive ranking of available models.

## Diagnostic content review

This review was generated by the coding agent, without an independent human
Bengali evaluator, gold labels or calibrated numeric quality scores. EN/BN/BN-CS
recovery prompts are synthetic and concern a complete immutable journal between
02:00 and 09:00, safe evidence preservation, isolated replay/validation, and the
difference between exposure and certain irreversible loss.

- Qwen: readable Bengali and Bengali-matrix code-switching; restores/replays and
  validates before cutover. EN fails to explicitly explain the seven-hour exposure
  and preserves backup media without clearly cloning the corrupted database.
  BN introduces journal incompleteness despite the given complete journal and
  adds explanation outside four steps. BN-CS is verbose, mistranslates the vendor
  repair as a repair record and does not clearly preserve the journal separately.
- Gemma: concise coherent Bengali and code-switching; EN explicitly preserves
  corrupted database and journal, and distinguishes exposure from confirmed loss.
  EN still adds an unnecessary repair after journal replay. BN does not clearly
  state why the complete journal avoids certain irreversible loss. BN-CS asserts
  the database was corrupt throughout the entire interval, which was not given,
  and does not explicitly preserve the journal before destructive action.
- Both retrieve all six extended-context controls, including superseded retention,
  pending production approval and absence of latency evidence. Neither invents
  authorization in that probe. This limited success does not establish broad
  long-context robustness.

The observed mistakes are reasons to retain rigorous RIU scoring and human QA.
They are not corrected, translated or used to revise frozen study prompts/gold.
Both candidates remained technically usable and followed the requested language;
no content error or truncation was silently treated as an infrastructure success.
The four smaller cached contenders retain their earlier FP32 CPU evidence, which
showed language/instruction limitations. This continuation does not claim a BF16
GPU quality comparison against every smaller contender. The larger distinct-family
pair is preferred on the combined observed comprehension, synthesis, capacity and
feasible deployment, rather than on size or speed alone. No universal strongest-model
claim is made. Official cards provide context, not Bengali validation:
[Qwen](https://huggingface.co/Qwen/Qwen3.5-9B),
[Gemma](https://huggingface.co/google/gemma-4-12B-it).

## Runtime and failure evidence

Both use native templates, greedy decoding, seed 20261023, thinking disabled,
SDPA, 1,024-token native chunked prefill, no CPU offload, one sequence, and
`PYTORCH_ALLOC_CONF=expandable_segments:True`. All loaded parameters are CUDA.
Qwen uses the native reference PyTorch recurrent/conv kernels: optional optimized
`causal_conv1d` / `flash-linear-attention` are absent. Rates describe this exact
runtime. Native Transformers was selected because it supports both cached
checkpoints without conversion or remote code and permits identical benchmark
and server paths. vLLM was not benchmarked; llama.cpp conversion/quantization was
unnecessary for the observed BF16 memory fit. No speed comparison to those engines
is implied. All exact package versions are in `gpu/requirements-cu130.lock.txt`.

Weight SHA256 and small-file Git blob hashes match the exact upstream revisions;
see `gpu/UPSTREAM_ARTIFACTS.json` and `gpu/ARTIFACT_VERIFICATION.json`. Cache blob
basenames are not assumed to equal upstream LFS SHA256. No weight downloads,
replacements, conversions or quantization were needed.

Preserved failures (`gpu/FAILED_RUNS.json` links ignored raw logs by SHA256):

1. Initial Qwen startup incorrectly assumed cache basename equals LFS content hash;
   corrected verification proves bytes match upstream. This was not corrupt weights.
2. Gemma unchunked prefill OOM at 40,960 and again at 34,816 despite expandable
   allocator segments. Native chunked prefill resolves the measured workspace peak.
3. An exploratory capacity prompt requested one-word READY while forcing 64 tokens,
   suppressing natural EOS and inducing channel restarts. The visible parser refused
   it and preserved raw output. The final capacity prompt requests substantive
   synthesis; the production parser still refuses unexpected reasoning markers.
4. Early exploratory runtime hashes were captured from the on-disk source during
   development; those logs are not the final reproducibility evidence. Final runs
   capture source hashes at module import and match the committed source exactly.

Real server smoke tests use the same GPU runtime and loopback runner adapter,
check exact model/revision/artifact provenance, reuse identical requests without a
second generation, and reject wrong-model requests and every frozen study prompt
in diagnostic mode. See `gpu/ADAPTER_SMOKE.json`. Study mode additionally requires
approved immutable manifest, spending authorization, all runtime settings and a
passing isolated judge gate. GPU and partition locks prevent competing local runs.
