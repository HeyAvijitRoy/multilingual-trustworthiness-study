# Hardware and local-model candidate assessment

Assessment date: 2026-10-23. **Candidate research and diagnostic evidence only;
this document does not freeze two selected locals or authorize study generation.**
No study responses were generated by this work. Synthetic outputs remain in
ignored `.local/feasibility/`, outside evaluation response directories.

## Observed execution host

`python3 scripts/hardware_inventory.py` produced `HARDWARE_INVENTORY.json` before
runtime installation. `HARDWARE_INFERENCE_ENVIRONMENT.json` records the isolated
inference environment afterward. Both omit hostnames, usernames, serial numbers,
process identities, credentials, and absolute filesystem paths.

- Linux x86_64 KVM guest, AMD EPYC 7713 CPU model, 32 available logical CPUs with
  AVX2/FMA. Guest topology presents 32 one-core sockets; physical-host core
  allocation is unknown. This is the actual agent runtime, not verified access to
  the user's physical VS Code workstation.
- Approximately 115.14 GiB installed RAM and 95.5 GiB available at initial
  observation; no swap. Approximately 107.5 GiB disk free before installation.
  Values fluctuate; inventory JSON contains exact bytes and observation times.
- `nvidia-smi` is installed but cannot communicate with a driver. No NVIDIA device
  nodes or `/dev/dri` are visible. GPU model, total/free VRAM, driver, CUDA/ROCm
  access, and GPU thermals are **unavailable**, not presumed zero or an RTX 3080 Ti.
  CPU execution remains possible. No Metal backend on this Linux runtime.
  The failed `nvidia-smi` creates an `nvidia-caps` directory: initial inventory
  code incorrectly counted that directory as a device node. Both inventories
  retain an explicit correction record and the original path-presence flag;
  the collector now counts only character-device nodes.
- No Ollama, llama.cpp, LM Studio CLI, or vLLM executable was found. Base Python
  3.12.3 had Transformers 5.8.0 but no torch/accelerate inference backend.
  CPU-only torch 2.14.1+cpu, Transformers 5.8.0, accelerate 1.15.0, tokenizers
  0.22.2 and safetensors 0.8.0 were installed into ignored
  `.local/inference-venv`. This diagnostic environment differs from the study's
  reference Python 3.11 and must be recorded if adopted.
- CPU load and pressure snapshots are in inventories. Workload identities were
  deliberately not collected. Power limits and thermal throttling could not be
  measured from this guest. Root cgroup quota files are unavailable, so no claim
  of an unrestricted exclusive physical host is warranted.

Initial sandbox package installation failed DNS resolution. The ordinary
`require_escalated` network path subsequently installed the CPU wheel and small
dependencies successfully. No credentials or proxy settings were changed, no
model weights were downloaded, and no license acceptance was performed.

Memory estimates are calculations from cached configuration, not measured peak
allocation: `2 × full_attention_layers × KV_heads × head_dim × bytes × context`,
plus bounded sliding-attention cache where applicable. The factor two is a
conservative separate-K-and-V estimate; Gemma 4 global shared-KV implementations
may use less. Qwen linear-attention recurrent/conv state is additional. Activations,
attention workspaces, logits, allocators, file mappings and engine overhead also
require headroom. FP32 weight estimates double on-disk BF16 sizes and approximate
auxiliary components. Actual RSS is reported separately; file sizes are not GPU
memory measurements.

All six are RAM-plausible sequentially at moderate context. The 9B/12B options are
deferred pending throughput evidence, not rejected as impossible. Q4/Q8 GGUF
variants could reduce weight memory (approximately 0.5/1 byte per parameter plus
scales/metadata), but no specific quantized artifact or llama.cpp revision has
been tested or approved. No Q4 quantization is silently applied to the cached
BF16 checkpoints; diagnostics explicitly convert to FP32 on CPU.

[Qwen's 2B card](https://huggingface.co/Qwen/Qwen3.5-2B) describes a post-trained
hybrid DeltaNet/attention model and 201-language/dialect coverage.
[The 4B card](https://huggingface.co/Qwen/Qwen3.5-4B) reports IFEval 89.8,
LiveCodeBench v6 55.8, and aggregate MMMLU 76.1; these provider results motivate
testing a larger checkpoint. They do not establish Bengali technical safety or
BN-CS ability under this study's greedy, nonthinking settings.

[Gemma 4 E2B](https://huggingface.co/google/gemma-4-E2B-it) and
[E4B](https://huggingface.co/google/gemma-4-E4B-it) use sliding/global attention
and large per-layer embeddings; "E2B" and "E4B" are effective sizes, not total
weight counts (approximately 5.1B and 8B including embeddings). The E4B card
reports stronger aggregate multilingual and coding performance than E2B, while
its 128k needle-retrieval score remains limited. This is proxy evidence, not a
Bengali/code-switch or critical-omission validation. Broad multilingual claims
do not resolve Bengali fluency, code-switch comprehension, cybersecurity judgment,
or constraint tracking; synthetic diagnostics and independent language review
remain necessary.

The linked Qwen3.5 and Gemma4 cards identify Apache-2.0 licenses. Preserve upstream
license/notice obligations for redistribution; this assessment distributes no
weights. Earlier [Gemma 3](https://huggingface.co/google/gemma-3-4b-it) uses custom
Gemma terms and an access gate, so its licensing must not be generalized to Gemma4.
Qwen3-8B/Gemma3-4B were considered as earlier-generation alternatives; current
cached Qwen3.5/Gemma4 avoid an unnecessary download and Gemma4 natively supports
the shared system role. This is a deployment-heterogeneous comparison, with no
claim of capacity matching to frontier cloud models.

## Diagnostic procedure and boundaries

`scripts/local_feasibility_benchmark.py` loads only an exact cached revision,
uses native tokenizer/chat template with `enable_thinking=False`, the unchanged
shared system instruction, FP32 CPU, 16 intra-op/one inter-op threads, greedy
decoding, seed 20261023, no tools, batch size one, and max 128 generated tokens.
It hashes weights/templates/tokenizers before loading and appends each observation
to a newly created diagnostic JSONL. Peak RSS is Linux process high-water RSS;
GPU memory is unmeasured. Time-to-first-token includes prefill plus the first
decode; effective prefill and subsequent decode rates are reported separately.
Load times use an already cached filesystem and exclude hashing/tokenizer setup.

There are three newly authored EN/BN/BN-CS backup-integrity arithmetic probes and
a separate 4k-token synthetic retrieval probe. The initial Qwen2B prompts omitted
a brevity constraint and all short responses hit 128 tokens. To obtain complete
short diagnostics, version `synthetic-backup-0.2` requests at most 30 words and
five words/check. Original raw records and script text remain preserved locally;
results from different diagnostic versions are not a controlled quality ranking.
No reserved study responses inform candidate selection.

Corpus access is token counting only over all 1,500 unchanged frozen prompts.
With the native Qwen2B template the longest is 1,307 tokens; GemmaE2B yields 508
(both SYN100 BN). The corresponding minimum prompt-plus-32,768-output capacities
are 34,075 and 33,276 tokens. A 65,536-token runtime allocation provides headroom;
32,768 total context would be insufficient. The 4k input probe covers the observed
maximum prompt length, but neither that probe nor a 128-token output smoke run
validates a 32,768-token decode or stability across 471 responses. No prompt is
truncated or altered for these token counts.

Observed results and candidate recommendations are recorded in
`LOCAL_FEASIBILITY_SUMMARY.json` when complete. Manual inspection in this report
is AI inspection, not human validation or study scoring. A final two-local choice
must pin the actual engine, dtype/quantization, context, tokenizer, stops and visible
response parser, and obtain the required amendment review before study execution.

Template/stop detail from the actual cache: Qwen's disabled-thinking template
includes an empty `<think>...</think>` block in the prompt prefix. Its tokenizer
EOS is `<|im_end|>` (248046), while model config EOS is `<|endoftext|>` (248044)
and no generation configuration is cached. The initial default-EOS diagnostics
emitted both special tokens; a future frozen adapter must explicitly terminate
on the intended assistant-turn EOS and avoid scoring delimiters. Gemma's disabled
thinking template ends at the native model turn; its generation configuration
stops at IDs `[1, 106, 50]`. Pin these differences and parse special tokens without
exposing internal thought channels. Historical diagnostics remain unedited.

AI inspection of the raw diagnostics found material limitations:

- Qwen2B initial: every short output hit the deliberately small 128-token cap.
  BN did not reach its arithmetic answer or checks; BN-CS began and continued in
  English despite the Bengali response instruction. This motivates withholding
  recommendation, but initial/v0.2 comparisons are confounded by prompt brevity.
- Qwen4B v0.2: EN returned 36 and three short numbered checks. BN returned 36 but
  substituted groups of file numbers for integrity checks; BN-CS supplied labels
  for archive/backup/integrity rather than actionable verification checks.
- GemmaE2B v0.2: correct 36 and Bengali in BN/BN-CS, but EN offered vague integrity
  wording without three numbered checks; BN used unnumbered comma-separated
  checks. BN-CS had three numbered terse checks with limited substance.
- GemmaE4B v0.2: correct 36 and numbered lists, but BN instructed renaming and
  copying files, violating the explicit read-only constraint. Its BN-CS list
  mixed a Bengali answer with English check phrases. Larger size did not remove
  the observed instruction-following problem.

These are observations from one diagnostic per language, not quantitative
capability estimates, human language judgments, omission scores, or an exclusion
threshold established in advance. **No pair is selected or frozen.** Qwen2B is
not preferred after its language/cap limitations; Qwen4B and both Gemma candidates
need broader independently reviewed diagnostics and a defensible selection rule.
Qwen9B/Gemma12B remain unbenchmarked alternatives. No further contenders or
outcome-generating runs were started in this session.

Median short-probe decode rates were approximately 2.66, 1.43, 1.45 and 1.11
tokens/s for Qwen2B, Qwen4B, GemmaE2B and GemmaE4B respectively. At 1,000 output
tokens/cell, a serial 471-response partition extrapolates to approximately
49/91/90/118 hours, excluding prefill, longer-cache slowdowns, retries and
contention. Using the entire 32,768-token allowance extrapolates to approximately
67/125/123/160 days per partition. These are arithmetic projections, **not
observed completed partitions or reliable worst-case bounds**. A single full-cap
response would exceed the historical 900-second timeout substantially. Local
timeout behavior needs an explicit amendment; a shorter allowance must not be
silently substituted. A verified local generation adapter with response parsing,
resume, errors, and full-context/output checks is still a gate to study execution.

```bash
.local/inference-venv/bin/python scripts/local_feasibility_benchmark.py --model google/gemma-4-E4B-it --revision ee0ef6023621cff504d758262d4e04895a5af4a2 --output .local/feasibility/gemma4-new-run.jsonl --threads 16 --max-new-tokens 128 --long-context-tokens 4096
```

The current runner explicitly unions tokenizer/model EOS IDs; the recorded Qwen
runs used model-default EOS. A rerun therefore has a documented stop-policy
difference and is not represented as byte-identical reproduction. Prompt texts,
hashes, original-script hash and long-probe construction are committed in
`DIAGNOSTIC_PROMPTS.json`; all run-specific weight/template hashes and measured
metadata are in `LOCAL_FEASIBILITY_SUMMARY.json`. Full diagnostic outputs and the
two earlier script versions remain local and append-only. Five no-inference
sanitization/isolation/provenance tests pass with
`python3 scripts/test_hardware_diagnostics.py`; all three new scripts compile.

## Exact requested Google model: documentary verification only

Google lists stable **`gemini-4-argon`** with a unified 1,048,576-token window and
65,536 synchronous output limit; thinking levels are low/medium/high.
[Official model specification](https://ai.google.dev/gemini-api/docs/models/gemini-4-argon).
The [migration guide](https://ai.google.dev/gemini-api/docs/latest-model) says
sampling controls temperature/top_p/top_k are ignored, and the output limit covers
thinking plus visible answer. Keep medium reasoning fixed if preserving the
historical control; do not expose thought blocks to scoring. GenerateContent is
still documented, although Interactions is the quickstart API.

Standard paid-tier input/output prices through 2026-11-30 are **$2/$10 per million
tokens**; output billing includes thinking. From 2026-12-01 they are **$4/$20**.
No free tier for this model. Do not assume caching or batch discounts in a
conservative standard-call budget.
[Official pricing](https://ai.google.dev/gemini-api/docs/pricing).
This verifies public documentation, not the current account's entitlement,
credentials, quota, SDK compatibility or successful model invocation. No paid
request or substitute model was used for this assessment.
